# Release Readiness R002 — Production Trust Root and Offline Signing Ceremony

Status: ready for non-secret implementation; production signing/activation blocked on maintainer-supplied key and R001 safe source/draft handoff.
Repository baseline: `dbowm91/wg-basic@ff40f851508ccda52171c27cefdcdaf4ec1da2d5` (2026-10-09).
Source roadmap: `plans/subsystems/release-readiness-security-roadmap.md`.
Primary class: invariant / security / release operations.
Authority: ADR-006; `plans/closure/distribution/001-status.md`, `003-final-status.md`, `004-status.md`, `005-status.md`.
Interface dependency: R001 source/tag/asset identity receipt and qualified stage workflow; non-secret fixture development can run in parallel. Operational hard blockers: R001 strict closure before actual production signing, maintainer key custody/out-of-band public-key authentication, and authorized draft signing.

## 1. Objective

Create a reviewed and repeatable **offline, maintainer-authorized** signing and key-provisioning workflow binding the exact Eggpack release manifest and POSIX installer bytes to an independently verified source revision, then embed the authentic public verification key in the release binary and docs. The production private key must remain outside source control, normal GitHub Actions, generated scripts, containers, and test fixtures. No public artifact or updater is called authentic until a real detached signature is validated by the production trust root.

## 2. Current evidence / trust-gap analysis

- `src/release.rs` deliberately declares `PRODUCTION_PUBLIC_KEY: Option<&str> = None`. Production `update check` and `update run` refuse before network; tests exercise fixture signing only.
- ADR-006 §7 requires project-controlled Minisign/Ed25519, private key retained out of band, a committed embedded public key and independently published fingerprint, a draft-signature gate, and exact source/version/target identity.
- `scripts/verify-signing-request.py` confirms unsigned Eggpack draft staging receipt entries, manifest identity, two selected GNU target asset digests, sidecars and every byte in the receipt inventory. This is a useful *consistency checker*, but does not itself authenticate GitHub release authorship, tagged commit, workflow run provenance, upstream source dependencies, or the person authorizing signing.
- `release/eggpack/install.sh` currently downloads and runs an unverified installer script in convenience mode. R003 owns the user-facing bootstrap policy; R002 must sign the `install.sh` that users verify out of band and also verify the final bundle before any release authorization.
- Public release naming must bind Cargo `X.Y.Z`, git tag `vX.Y.Z`, binary `wg-basic --version`, Eggpack release ID and exact source SHA. The repository currently declares `version = "0.1.0"`. This is not authority to publish a 0.1.0 tag without a maintained version decision and immutable tag checks.

## 3. Trust and key ownership invariants

1. Only the human maintainer or an explicitly authorized trusted signer controls the private Minisign key. It MUST NOT be generated by a planning agent, committed, uploaded to regular CI artifacts/logs, or provided as an ordinary GitHub Actions secret. Never automate irreversible publication without explicit authorization.
2. Public verification key is committed and embedded only after independent key custody and fingerprint confirmation. Record its full canonical Minisign public-key text, key ID/fingerprint and an out-of-band distribution channel. Do not mistake a checksum of unsigned key text for key authenticity.
3. The exact unsigned manifest bytes must be verified against a genuinely independent trusted source/tag identity and qualified build receipts before signing. Self-consistency of two attacker-controlled files does not establish provenance.
4. Detached signatures cover manifest and `install.sh` exactly, using established Minisign signature format; avoid mutable release notes or post-sign transformations of signed bytes. A signature on an installer is not a signature on every arbitrary bootstrap URL or execution context; document script trust separately.
5. Runtime updater accepts exactly the embedded production key(s) according to explicit rotation policy, unsigned legacy downgrade is forbidden, and signature verification precedes parsing/projection/acquisition.
6. A private key loss/revocation or compromised tagged release produces a documented stop/incident path; no silent trust-key replacement, no automatic unsigned recovery channel.
7. A test key remains test-only and never activates production mode; verify release binary has no fixture key, fixture transport selector, or unsigned URL override.

## 4. Ordered work packages

### WP1 — Offline signing inputs and provenance preflight

Write `scripts/verify-release-signing-bundle.py` (or a comparably bounded tool) to ingest R001's trusted source/run receipt, independently retrieved tag SHA and immutable staging assets. Re-run `scripts/verify-signing-request.py` for exact byte inventory and then independently assert:
- repository owner/name, stable tag, source SHA and Cargo package/binary version match;
- source commit is approved for release and tagged at exactly the signed revision;
- **current** native x86_64 and aarch64 build/qualification and release-contract workflow evidence reference that same SHA and target digests, and workflow run identity/attempt;
- required installer/manifest, sidecars, final binary files, staging receipt and optional attestation inventory are complete, filenames/case and exact bytes unambiguous, no symlink/hardlink/path traversal in local bundle;
- all artifacts are from the same authorized draft and no new/rewritten asset appeared after receipt validation.

Do not assert cryptographic provenance merely because a GitHub JSON receipt includes a source SHA. Authenticated external evidence may be obtained through a maintainer-verified GitHub API/CLI session plus immutable workflow metadata and, if provided, GitHub OIDC artifact attestations. OIDC provenance is additive, not a replacement for the offline release signature.

### WP2 — Production public-key interface with fail-closed default

Implement a minimal, reviewable `src/release.rs` public-key provisioning seam: preferred explicit checked-in canonical public key in source plus a verified full fingerprint; keep `None` until the maintainer supplies it and source review confirms the key. If build-time embedding is used, ensure ordinary builds cannot silently source an arbitrary environment key and that normal CI no-key behavior still fails closed. Avoid a build option that lets users set an untrusted key for normal updates.

Add static/type regression to guarantee no test key in a production release and to reject malformed production public key, truncated signature, wrong release key, and mismatched manifest. Retain the project-owned trust key without delegating authentication to GitHub alone.

### WP3 — Offline operator ceremony (two-person or equivalent explicit approval)

Document in `docs/release-signing.md` an operator-facing ceremony:
1. trusted-key generation/key custody by maintainer on a segregated system, public-key authentication, separately secured backup and rotation/revocation policy;
2. release/tag freeze and independent attestation of source SHA, target artifacts, CI gates, unsigned manifest and installer inventory;
3. transfer exact approved bytes to signing host via authenticated channel without moving private key;
4. signer validates all SHA-256 and identity/provenance constraints, reviews intended release ID, executes Minisign detached signing separately for `release-manifest.json` and `install.sh`, records canonical fingerprints/signatures;
5. independently re-verifies both signatures with only the committed public key, without access to the signing private key;
6. uploads ONLY approved `.minisig` assets to draft through a bounded maintainer-authorized path; fetches every published draft asset back and re-verifies exact bytes/signatures, source OID and staged manifest;
7. records human approval/abort, signed receipts, release notes/fingerprint instructions and disaster recovery contact/path without disclosing secrets;
8. explicit, separate `publish` action only after R004 release authorization.

No signing action or actual key provisioning is part of this planning handoff.

### WP4 — Threat-focused negative matrix

Test wrong-key, wrong-tag, wrong-release, wrong-product, unsigned, truncated/minisig-surplus, corrupted asset, swapped platform binary, absent signature, mutable source/tag, insufficient CI provenance, draft asset replacement after receipt, stale run, duplicate file name, signed wrapper with mismatched generated bootstrap, and untrusted output directory. Make the negative cases fail before any signing/upload/staging mutation. Include valid fixture signing end-to-end to verify functional wiring.

### WP5 — Operating docs and repeatability

Write a deterministic checklist with exact commands and evidence paths for independent verification (Git tag/commit/Cargo version, Minisign `-Vm`, approved fingerprint, both artifact SHA256, native release smoke and systemd lifecycle job IDs). Note that raw Minisign public keys/fingerprints are public, never distribute the secret key. Capture key custody arrangements outside the repo while allowing nonsecret metadata to be recorded.

## 5. Failure, restart, migration and operational policy

If verification fails, stop without signing or mutating a draft. On partial signature upload, do not assume draft is ready; fetch the entire asset list, validate the authorized manifest/signatures again and classify block. A compromised key requires stop/rotate only through a separately reviewed trusted distribution process; an installed old binary cannot silently accept a new key without a signed transition anchored to the trusted old key or an explicit out-of-band reinstall. Release artifact filenames and CLI must remain stable unless an ADR supersedes ADR-006.

```text

```

Run updated distribution-foundation source/manifest checks and both native GNU target artifact lifecycle tests at the *exact* release candidate commit. The real ceremony must use a signed draft that was independently verified; a fixture-only run is qualification of mechanics, not operational release readiness. No private key material may be added to CI logs, artifacts, test fixtures, or pull requests.

## 7. Security and compatibility

No additional root/systemd privileges, WireGuard/management protocol changes, or relaxed service identity. Key material transition is an explicit trust decision, not a routine dependency bump. Public key is verifier data; private key is security-critical and remains out of band. If a new signature interface is proposed, keep it separate from the external Eggpack build producer and Eggup local transaction APIs.

## 8. Documentation, acceptance and stop conditions

Update `src/release.rs` only after key custody approval; add `docs/release-signing.md`, `docs/installation.md`, `architecture/update-rollback-contract.md`, release documentation and `plans/subsystems/release-readiness-security-roadmap.md`. Nonsecret tooling may close as technically implemented while **production signing remains blocked**; record two separate dispositions.

R002 technical acceptance requires: independent trusted source-run-artifact binding, valid offline Minisign verifier with wrong-key/tamper controls, no normal-CI private key, explicit stored fingerprint/key rotation plan, repeatable fail-closed signing procedure, and artifact/signature re-download tests. R002 operational closure requires maintainer-provisioned actual key, matched embedded public key, and a real production-signed draft from R001-qualified source. No R004 release authorization until both are proven.

Stop for a scoped design review if draft provenance cannot be independently established, byte equality cannot be reproduced, the first release tag/commit selection is ambiguous, key sharing is proposed, a fixture key can enter a production build, provenance tool depends only on untrusted JSON, or signing becomes coupled to write-authorized CI without explicit maintainer consent.
